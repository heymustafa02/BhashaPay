# BhashaPay

BhashaPay is a pay-per-call marketplace for Indic-language AI services, with an autonomous agent that discovers registered services and pays for them through x402 on Hedera or EIP-3009 USDT settlement on Whitechain Sepolia.

For prerequisites and full local run instructions, see [setup.md](./setup.md).

## Hedera x402 translation endpoint

`POST /translate` is protected with the official x402 `exact` scheme on Hedera testnet. It asks for 0.01 test USDC (token `0.0.429274`, 10,000 units at six decimals), settles through the public x402 facilitator, and only then calls the configured Google Gemini translation API.

The x402 client signs the requested transfer with the payer's key. The facilitator verifies and settles it and pays the network fee. The API returns the translation only after x402 accepts the payment.

### Running it

1. Copy `.env.example` to `.env`.
2. Set `HEDERA_PAY_TO_ACCOUNT_ID` to a Hedera testnet account associated with testnet USDC.
3. Set `HEDERA_CLIENT_ACCOUNT_ID` and `HEDERA_CLIENT_PRIVATE_KEY` for a funded Hedera testnet payer. The payer must hold testnet USDC and be associated with `0.0.429274`.
4. Set `HEDERA_OPERATOR_ID`, `HEDERA_OPERATOR_PRIVATE_KEY` and `HEDERA_AUDIT_TOPIC_ID` for HCS payment auditing.
5. Set `GEMINI_API_KEY` for Google Gemini (optionally configure `GEMINI_MODEL`, `GEMINI_STT_MODEL` and `GEMINI_OCR_MODEL`).
6. Run `npm install`.
7. In separate terminals run `npm run api:dev` and `npm run dev`, then `npm run demo:translate` for the paid client.

Do not commit `.env` or use mainnet credentials.

### Limitations

- The direct x402 demo covers translation only. The agent also supports Hedera speech transcription and document OCR. Whitechain settlement currently supports translation only.
- Translation, transcription, OCR and agent service selection use the Google Gemini API and need `GEMINI_API_KEY`.
- Paid runs require configured accounts, an HCS topic, a seeded service registry and provider credentials.
- Agent service prices are seeded after the Whitechain registry is deployed. STT and OCR use Hedera and need a funded Hedera payer.

## Whitechain contracts

Whitechain Sepolia is chain ID `1874`, uses WBT for gas, and exposes its RPC at `https://rpc.testnet.whitechain.io/`. The USDT address is `0xcedfB56113143d55b2358b8CFbB0dEB5Ad2f55a7`. Its explorer-verified proxy implementation is `0x26425662d126412128967ecf0a02ec48573026f7`. The verified ABI includes EIP-3009 `transferWithAuthorization`, EIP-2612 `permit`, `authorizationState` and six-decimal USDT metadata. The settlement design uses EIP-3009, so the payer signs an authorization offchain and only the allowlisted relayer pays WBT gas.

Contracts under `contracts/`:

- `BhashaRegistry`: merchant service registry.
- `BhashaSettlement`: settlement with stored receipts, one-use request hashes, relayer amount limits, pause controls, merchant refunds and optional per-payer spend policies.
- `AgentSpendPolicy`: onchain spend policy for agent payers.

```bash
npm run contracts:test
```

**Deployment status:** none. See [`packages/shared/deployments.json`](./packages/shared/deployments.json) for the empty deployment fields. Whitechain's documented Foundry verification endpoint is `https://explorer.testnet.whitechain.io/api/`. Deployment requires test WBT from the official faucet. No deployment or explorer verification is claimed until a funded signer deploys and confirms it. ## Whitechain payment flow

The private facilitator in `services/facilitator-whitechain/` accepts authenticated requests from the API only. It:

1. Reads the live service price and active flag from `BhashaRegistry`.
2. Verifies the EIP-712 signature against the live Whitechain USDT domain (`Tether USD`, version `1`, chain ID `1874`).
3. Checks the authorization nonce and any attached onchain spend policy.
4. Calls `BhashaSettlement`, waits for one confirmation and checks the emitted receipt.
5. Returns a transaction hash and explorer URL, which the API validates independently before running the service.

The relayer private key is read only by the facilitator and is never returned.

The facilitator rate-limits by source IP, service and payer per minute. Contract-level allowlisting, request-hash replay protection, per-payment maximums and pausing are enforced independently of the HTTP layer. The idempotency hash binds the API idempotency key and payload hash to the onchain receipt, so repeating an already-settled request returns the existing receipt instead of charging again.

To run it once the registry and settlement are deployed and the environment is set, use `npm run api:dev` and `npm run whitechain:dev` in separate terminals. The agent signs a short-lived EIP-3009 authorization locally and posts it to `/whitechain/translate`. It does not sign a contract transaction or hold WBT.

This flow is implemented but has **not** been submitted on testnet. No deployment, USDT payer key or funded relayer is configured, so no successful or rejected onchain transaction link is claimed.

## API, persistence and agent runs

The API stores services, runs, payments, receipts, run events and HCS audit references in SQLite at `DATABASE_PATH` (default `./data/bhashapay.sqlite`). `GET /registry` merges local metadata with live Whitechain registry entries. Seed services only after deploying the registry and setting its address and the merchant and payer configuration:

```bash
npm run services:seed
npm run api:dev
```

Endpoints: `GET /health`, `GET /registry`, `POST /runs`, `GET /runs/:id`, `GET /runs/:id/events` (SSE), `GET /payments`, `GET /receipts/:id`, `POST /approvals/:paymentId` and `GET /audit`. A run request uses decimal USDC/USDT amounts as strings:

```json
{
  "task": "Translate this Marathi text to English",
  "budget": "0.50",
  "policy": {
    "perMerchantLimit": "0.25",
    "merchantAllowlist": ["0.0.12345"],
    "approvalThreshold": "0.10"
  },
  "input": {
    "text": "नमस्कार",
    "sourceLanguage": "Marathi",
    "targetLanguage": "English"
  }
}
```

Idempotency keys are required for direct paid requests. Whitechain settlement keys are bound to the payer, service and request payload. Hedera requests are persisted before the payment middleware, and a reused key returns the recorded result instead of settling again. Payment attempts are blocked unless an HCS topic and operator credentials are configured, and the audit API reads messages from the Hedera testnet mirror node. Set `FRONTEND_ORIGIN` to the exact dashboard origin before exposing the API.



## Dashboard

The Next.js dashboard lives in `apps/web/`. Run it with `npm run dev`, setting `NEXT_PUBLIC_API_URL` if the API is not at `http://localhost:4021`. Pages: `/` (overview), `/marketplace`, `/agent` (run form, SSE timeline and approval modal), `/payments` and `/audit`. It uses the configured backend origin and contains no wallet or server keys. It has explicit loading, empty, API error, denied and approval states. The production build is verified locally; no testnet transaction has been produced from the UI.
